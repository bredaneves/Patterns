Singleton

Um único gerente para toda a pizzaria — e por que isso importa

O problema que o Singleton resolve
Alguns recursos do sistema precisam existir em uma única instância. Criar mais de uma causa inconsistências, desperdício ou comportamento imprevisível.
Exemplos reais:

— Pool de conexões com o banco: se cada classe criar o seu próprio, você abre centenas de conexões desnecessárias.

— Logger: se cada módulo criar um logger diferente, os logs vão para lugares diferentes e perdem a ordem cronológica.

— Configuração da aplicação: se cada parte ler e guardar as configs separadamente, uma pode ter valor diferente da outra.

— Fila de pedidos de uma pizzaria: se existirem duas filas paralelas, os atendentes não sabem qual seguir.
O Singleton garante: apenas uma instância da classe existe em toda a aplicação, e qualquer parte do código que precisar dela vai receber sempre a mesma.

As duas responsabilidades do Singleton

1. Impedir que new seja chamado diretamente
+
2. Oferecer um ponto de acesso global à instância única
A analogia da pizzaria
A pizzaria tem um único Gerente de Pedidos. Ele controla a fila, o estoque e a ordem de produção. Não faz sentido ter dois — causaria caos.
Cenário sem controle:

Atendente 1 abre sua própria fila de pedidos.
Atendente 2 abre outra fila separada.
Pizzaiolo não sabe qual fila seguir.
Pedido 5 da fila 1 conflita com pedido 5 da fila 2.
Resultado: caos, pedidos perdidos, cliente insatisfeito.
Com Singleton: existe um único Gerente de Pedidos. Qualquer atendente que precisar registrar um pedido acessa sempre o mesmo gerente — e ele mantém a fila consistente para toda a pizzaria.

Sem Singleton — o que acontece
Cada atendente cria seu próprio gerente. A fila fica fragmentada.
Java// Sem Singleton — qualquer um pode criar uma instância nova class GerentePedidos { private List<String> fila = new ArrayList<>(); public void adicionarPedido(String pedido) { fila.add(pedido); System.out.println("Pedido adicionado: " + pedido); } public void mostrarFila() { System.out.println("Fila atual: " + fila); } } // Atendente 1 cria SEU gerente GerentePedidos gerente1 = new GerentePedidos(); gerente1.adicionarPedido("Pizza Calabresa"); gerente1.adicionarPedido("Pizza Frango"); // Atendente 2 cria OUTRO gerente — objeto diferente! GerentePedidos gerente2 = new GerentePedidos(); gerente2.adicionarPedido("Pizza Margherita"); // Pizzaiolo pergunta pela fila — mas qual gerente consultar? gerente1.mostrarFila(); // Fila atual: [Pizza Calabresa, Pizza Frango] gerente2.mostrarFila(); // Fila atual: [Pizza Margherita] // A pizza Margherita sumiu da visão do gerente1! // Dois estados diferentes — inconsistência total.
O problema: gerente1 e gerente2 são objetos diferentes na memória. Cada um tem sua própria fila. Nenhum enxerga os pedidos do outro. O estado da aplicação ficou partido em dois.
Com Singleton — a solução
O construtor é privado. A única forma de acessar o gerente é pelo método estático getInstance(), que cria a instância na primeira chamada e reutiliza nas demais.
Javaclass GerentePedidos { // 1. A única instância fica guardada aqui — estática e privada private static GerentePedidos instancia = null; private List<String> fila = new ArrayList<>(); // 2. Construtor PRIVADO — ninguém de fora pode chamar "new" private GerentePedidos() {} // 3. Ponto de acesso global — cria só se ainda não existe public static GerentePedidos getInstance() { if (instancia == null) { instancia = new GerentePedidos(); // cria UMA vez } return instancia; // sempre retorna a mesma } public void adicionarPedido(String pedido) { fila.add(pedido); System.out.println("Pedido adicionado: " + pedido); } public void mostrarFila() { System.out.println("Fila atual: " + fila); } } // Atendente 1 acessa o gerente GerentePedidos g1 = GerentePedidos.getInstance(); g1.adicionarPedido("Pizza Calabresa"); g1.adicionarPedido("Pizza Frango"); // Atendente 2 acessa — recebe O MESMO objeto GerentePedidos g2 = GerentePedidos.getInstance(); g2.adicionarPedido("Pizza Margherita"); // Pizzaiolo consulta — estado unificado g1.mostrarFila(); // Fila atual: [Pizza Calabresa, Pizza Frango, Pizza Margherita] g2.mostrarFila(); // Fila atual: [Pizza Calabresa, Pizza Frango, Pizza Margherita] // Confirmando que são o mesmo objeto na memória System.out.println(g1 == g2); // true
O que mudou: o construtor é privado — ninguém pode chamar new GerentePedidos(). O getInstance() é a única porta de entrada. Na primeira chamada cria; nas seguintes, devolve a mesma. Um único estado para toda a aplicação.
Cuidado: Singleton em ambiente multithread
A implementação básica tem uma falha: se dois atendentes chamarem getInstance() ao mesmo tempo, antes da instância ser criada, podem acabar criando dois objetos.
O problema de corrida (race condition):

Thread A verifica: instancia == null → verdadeiro → vai criar
Thread B verifica: instancia == null → verdadeiro → vai criar também
Resultado: dois objetos criados. O Singleton quebrou.

Solução 1 — synchronized (simples, mas mais lento)

Javapublic static synchronized GerentePedidos getInstance() { if (instancia == null) { instancia = new GerentePedidos(); } return instancia; } // Garante exclusividade, mas bloqueia todas as threads em cada chamada.

Solução 2 — Double-checked locking (recomendada)

Javaprivate static volatile GerentePedidos instancia = null; public static GerentePedidos getInstance() { if (instancia == null) { // 1ª verificação — sem lock synchronized (GerentePedidos.class) { if (instancia == null) { // 2ª verificação — com lock instancia = new GerentePedidos(); } } } return instancia; } // Bloqueia só na criação. Depois, acesso sem custo.

Solução 3 — Initialization-on-demand (a mais elegante em Java)

Javaclass GerentePedidos { private GerentePedidos() {} // A JVM garante que esta classe interna é carregada uma única vez private static class Holder { static final GerentePedidos INSTANCIA = new GerentePedidos(); } public static GerentePedidos getInstance() { return Holder.INSTANCIA; } } // Thread-safe sem synchronized. Criação lazy. Sem volatile. Preferida.
Para o dia a dia: use o padrão Holder (solução 3) quando precisar de Singleton thread-safe em Java. É a mais limpa e a JVM cuida de toda a sincronia.
Quando usar — e quando evitar
O Singleton é o padrão mais simples de entender e o mais fácil de usar errado.

Use Singleton quando...

— Um único ponto de controle faz sentido no domínio (fila, log, config, cache, pool de conexões).

— O objeto é caro para criar e pode ser compartilhado com segurança.

— O estado precisa ser consistente em toda a aplicação.

Evite Singleton quando...

— Você só quer evitar passar parâmetros entre classes — isso é acoplamento disfarçado.

— O objeto tem estado mutável acessado por muitas threads sem controle.

— Você quer facilidade de testes unitários — Singleton dificulta mocking.

E se perguntarem "quando você não usaria Singleton?" — dificuldade de testar unitariamente é a resposta que os avaliadores mais valorizam.
Onde você já viu Singleton sem saber: o ApplicationContext do Spring é gerenciado como Singleton por padrão — cada bean que você declara com @Service, @Repository ou @Component é, na prática, um Singleton dentro do container.
