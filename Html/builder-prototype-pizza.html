Builder & Prototype

Dois padrões de criação — mesma pizzaria, problemas diferentes

Builder — o problema que ele resolve
A pizzaria agora aceita pedidos personalizados. O cliente escolhe cada detalhe: tamanho, massa, molho, queijo, ingredientes extras, borda recheada ou não.
Sem o Builder, como você criaria esse objeto?

Opção 1 — construtor gigante:
new Pizza("grande", "fina", "suave", "mussarela", true, "calabresa", "azeitona")

Problema: 7 parâmetros. Qual é o quinto? Borda recheada? Queijo extra? Impossível saber sem olhar a assinatura do construtor toda vez.

Opção 2 — setters em cadeia:
pizza.setTamanho(...); pizza.setMassa(...); pizza.setMolho(...);

Problema: o objeto fica "pela metade" durante a montagem. Nada garante que todos os campos obrigatórios foram preenchidos antes de usar a pizza.
O Builder resolve: ele monta o objeto passo a passo, em uma interface fluente e legível, e só entrega o objeto final quando você chamar build() — aí ele pode validar se está tudo certo.

Comparação com os outros padrões que você aprendeu:

Factory Method / Abstract Factory → decidem qual tipo de objeto criar.
Builder → decide como montar um objeto complexo, passo a passo.
Builder — código completo
A Pizza tem muitos atributos opcionais. O Builder monta ela de forma legível e segura.
Java// === PRODUTO === class Pizza { private final String tamanho; private final String massa; private final String molho; private final String queijo; private final boolean bordaRecheada; private final String ingredienteExtra; // Construtor privado — só o Builder pode criar private Pizza(Builder builder) { this.tamanho = builder.tamanho; this.massa = builder.massa; this.molho = builder.molho; this.queijo = builder.queijo; this.bordaRecheada = builder.bordaRecheada; this.ingredienteExtra = builder.ingredienteExtra; } public void descrever() { System.out.println("Pizza " + tamanho + ", massa " + massa + ", molho " + molho + ", queijo " + queijo + (bordaRecheada ? ", borda recheada" : "") + (ingredienteExtra != null ? ", extra: " + ingredienteExtra : "")); } // === BUILDER (classe interna) === static class Builder { // Obrigatórios private final String tamanho; private final String massa; // Opcionais com padrão private String molho = "clássico"; private String queijo = "mussarela"; private boolean bordaRecheada = false; private String ingredienteExtra = null; // Obrigatórios entram no construtor do Builder public Builder(String tamanho, String massa) { this.tamanho = tamanho; this.massa = massa; } // Cada método retorna o próprio Builder → encadeamento fluente public Builder molho(String molho) { this.molho = molho; return this; } public Builder queijo(String queijo) { this.queijo = queijo; return this; } public Builder bordaRecheada() { this.bordaRecheada = true; return this; } public Builder ingredienteExtra(String ingrediente) { this.ingredienteExtra = ingrediente; return this; } // Entrega o objeto final public Pizza build() { return new Pizza(this); } } } // === USO — leitura quase como linguagem natural === Pizza p1 = new Pizza.Builder("grande", "fina") .molho("suave") .queijo("mussarela") .bordaRecheada() .build(); p1.descrever(); // Pizza grande, massa fina, molho suave, mussarela, borda recheada Pizza p2 = new Pizza.Builder("média", "grossa") .molho("picante") .ingredienteExtra("pepperoni") .build(); p2.descrever(); // Pizza média, massa grossa, molho picante, mussarela, extra: pepperoni
O que o Builder garante: tamanho e massa são obrigatórios (entram no construtor do Builder). O resto é opcional com valor padrão. Você nunca entrega um objeto incompleto porque build() é o único caminho.
Builder — depois da expansão
A pizzaria quer oferecer combos prontos: "Italiana Clássica" e "Americana Especial" — configurações pré-definidas sem o cliente precisar escolher tudo.
Solução: criar um Diretor — uma classe que sabe como usar o Builder para montar configurações específicas. O Builder continua o mesmo.
Java// O Builder não muda. Criamos só um Diretor. class PizzaioDiretor { public Pizza montarItalianaClassica() { return new Pizza.Builder("grande", "fina") .molho("suave") .queijo("mussarela fresca") .build(); } public Pizza montarAmericanaEspecial() { return new Pizza.Builder("família", "grossa") .molho("picante") .queijo("cheddar") .bordaRecheada() .ingredienteExtra("bacon") .build(); } } // Uso com o Diretor PizzaioDiretor diretor = new PizzaioDiretor(); Pizza italiana = diretor.montarItalianaClassica(); Pizza americana = diretor.montarAmericanaEspecial();
Builder + Diretor: o Builder sabe como montar. O Diretor sabe o que montar. Você pode ter vários diretores (cardápio vegetariano, cardápio infantil) usando o mesmo Builder.
Prototype — o problema que ele resolve
A pizzaria tem um cardápio com pizzas que são quase iguais — a "Calabresa Dupla" é igual à "Calabresa" mas com dobro do ingrediente. Criar do zero toda vez é custoso e repetitivo.
Problema: você tem um objeto já configurado e quer criar variações dele sem reconfigurar tudo do zero. Copiar o objeto manualmente é trabalhoso e acoplado — você precisaria saber todos os atributos internos.
O Prototype resolve: o próprio objeto sabe como se copiar. Você chama clonar() e recebe uma cópia independente, que pode modificar sem afetar o original.

Diferença importante para o Builder:

Builder → monta um objeto novo do zero, passo a passo.
Prototype → copia um objeto que já existe e ajusta o necessário.
Prototype — código completo
A Pizza implementa uma interface Clonavel. Cada pizza sabe se copiar.
Java// === INTERFACE PROTOTYPE === interface Clonavel { Clonavel clonar(); } // === PRODUTO === class PizzaPrototype implements Clonavel { private String tamanho; private String massa; private String molho; private String queijo; private String ingrediente; public PizzaPrototype(String tamanho, String massa, String molho, String queijo, String ingrediente) { this.tamanho = tamanho; this.massa = massa; this.molho = molho; this.queijo = queijo; this.ingrediente = ingrediente; } // Construtor de cópia — usado pelo clonar() private PizzaPrototype(PizzaPrototype outra) { this.tamanho = outra.tamanho; this.massa = outra.massa; this.molho = outra.molho; this.queijo = outra.queijo; this.ingrediente = outra.ingrediente; } @Override public Clonavel clonar() { return new PizzaPrototype(this); } public void setIngrediente(String ingrediente) { this.ingrediente = ingrediente; } public void setTamanho(String tamanho) { this.tamanho = tamanho; } public void descrever() { System.out.println("Pizza " + tamanho + ", " + massa + ", " + molho + ", " + queijo + ", " + ingrediente); } } // === REGISTRO DE PROTÓTIPOS (cardápio base) === import java.util.HashMap; import java.util.Map; class CardapioPizzas { private Map<String, PizzaPrototype> cardapio = new HashMap<>(); public void registrar(String nome, PizzaPrototype pizza) { cardapio.put(nome, pizza); } public PizzaPrototype obter(String nome) { return (PizzaPrototype) cardapio.get(nome).clonar(); // sempre retorna CÓPIA } } // === USO === CardapioPizzas cardapio = new CardapioPizzas(); // Registra os protótipos base uma vez só cardapio.registrar("calabresa", new PizzaPrototype("média", "fina", "clássico", "mussarela", "calabresa")); cardapio.registrar("frango", new PizzaPrototype("média", "fina", "branco", "mussarela", "frango")); // Pedido 1: calabresa normal PizzaPrototype pedido1 = cardapio.obter("calabresa"); pedido1.descrever(); // Pizza média, fina, clássico, mussarela, calabresa // Pedido 2: calabresa dupla (cópia + ajuste) PizzaPrototype pedido2 = cardapio.obter("calabresa"); pedido2.setTamanho("grande"); pedido2.setIngrediente("calabresa dupla"); pedido2.descrever(); // Pizza grande, fina, clássico, mussarela, calabresa dupla // O original não foi afetado PizzaPrototype pedido3 = cardapio.obter("calabresa"); pedido3.descrever(); // Pizza média, fina, clássico, mussarela, calabresa ← intacto
O ponto central: o cardápio guarda os protótipos base. Cada pedido recebe uma cópia independente. Modificar o pedido nunca afeta o original — e você não precisa saber como a pizza é construída por dentro.
Comparação final — os 4 padrões juntos
Agora que você viu todos, aqui está o mapa de decisão.

Factory Method

A pizzaria decide qual pizza fazer. Você troca a pizzaria, troca o produto. Um único produto variável.

Abstract Factory

A pizzaria decide massa + molho + ingrediente juntos. Garante que nada mistura estilos diferentes.

Builder

O cliente monta a pizza passo a passo, escolhendo cada detalhe. O objeto só fica pronto no build().

Prototype

A pizzaria tem pizzas base no cardápio. Cada pedido é uma cópia que pode ser ajustada sem alterar o original.

Pergunta Use este padrão
Qual subclasse deve criar este objeto? Factory Method
Como garantir que objetos relacionados sejam compatíveis? Abstract Factory
Como montar um objeto complexo com muitas opções de forma legível? Builder
Como criar variações de um objeto que já existe sem reconfigurar tudo? Prototype
Onde você vai ver isso no mundo real:

Builder → StringBuilder, HttpRequest.Builder, configuração de clientes REST, montagem de queries SQL complexas.

Prototype → caching de objetos pesados (conexões, configurações de relatório), sistemas de templates de documentos, jogos onde inimigos são variações de um modelo base.
Dica para entrevistas: quando perguntarem sobre padrões de criação, conecte cada um a um problema real do seu trabalho com Datasul ou ERP. "No sistema de integração, usamos algo parecido com Builder para montar as mensagens XML de NF-e" — isso vale muito mais do que decorar a definição do livro.
